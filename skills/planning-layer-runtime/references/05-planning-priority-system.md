# Planning Priority System

## 1. Priority 定义

Priority 表示规划优先级与验收重要性。

Priority 不表示变更规模。
Priority 不表示测试执行顺序。

Change Level 使用 `S/M/L`。

Priority 使用 `P0/P1/P2`。

### P0

定义：

- 必须立即处理的阻塞事项。

特征：

- 影响核心业务闭环
- 影响上线门禁
- 影响安全、权限、数据正确性、状态一致性或关键验收
- 需要明确影响分析、验收口径和回滚策略

是否阻塞上线：是

是否必须回归：是

是否允许延期：否

示例：

- 核心流程无法完成
- 权限越权
- 数据写入错误
- 状态机非法迁移
- P0 验收范围未覆盖

### P1

定义：

- 重要但不默认阻塞上线的事项。

特征：

- 影响主要功能体验或局部业务效率
- 不破坏核心闭环
- 不引入高风险安全、权限、数据一致性问题
- 需要明确处理计划和验收口径

是否阻塞上线：条件阻塞

是否必须回归：是

是否允许延期：允许，经确认后延期

示例：

- 次要流程体验不完整
- 非核心接口错误提示不准确
- 局部列表筛选行为异常
- 重要但可绕行的联调问题

### P2

定义：

- 可延期处理的低优先级事项。

特征：

- 不影响核心业务闭环
- 不影响上线门禁
- 不影响安全、权限、数据正确性或关键验收
- 可进入 backlog

是否阻塞上线：否

是否必须回归：按需

是否允许延期：是

示例：

- 非关键文案优化
- 局部 UI 微调
- 非核心日志补充
- 可后续优化的操作便利性问题

## 2. Severity 定义

Severity 表示问题严重性。

Priority 表示规划优先级与验收重要性。

Priority 不等于 Severity。

| Severity | 定义 |
| --- | --- |
| Critical | 造成核心流程中断、安全风险、权限越权、数据损坏或不可恢复错误 |
| High | 明显影响主要功能、主要角色或重要业务路径 |
| Medium | 影响局部功能、局部体验或可绕行流程 |
| Low | 轻微体验、文案、样式或非关键优化 |

| 场景 | Priority | Severity |
| --- | --- | --- |
| 上线前发现权限越权 | P0 | Critical |
| 核心提交流程失败 | P0 | Critical |
| 关键列表筛选错误但可手动绕行 | P1 | High |
| 重要错误提示不清晰 | P1 | Medium |
| 按钮文案需优化 | P2 | Low |
| 非关键页面间距不一致 | P2 | Low |

## 3. Runtime Gate

### P0 Gate

上线前必须满足：

- P0 任务全部完成
- P0 验证全部通过
- P0 影响分析已记录
- P0 回滚策略已记录
- P0 遗留项为 0

该 Gate 由后续测试与验收承接方在验收阶段执行；planning-layer-runtime 只定义 P0 归属、验收口径、自动化等级、真实环境要求和预期证据要求。

### P1 Gate

上线前必须处理：

- 已完成的 P1 必须有下游验证结果
- 未完成的 P1 必须记录延期原因
- 未完成的 P1 必须确认不阻塞上线
- 未完成的 P1 必须进入后续任务或 backlog

### P2 Gate

上线前允许延期：

- P2 可进入 backlog
- P2 不得阻塞 P0
- P2 不得伪装为 P1/P0
- P2 延期必须保留来源和处理建议

## 4. Planning And Implementation Scheduling Rules

- P0 默认优先执行。
- P0 不允许被 P2 阻塞。
- P0 必须有明确验收口径，并由下游记录验证结果。
- P0 必须具备影响分析。
- P0 必须具备回滚策略。
- P1 在 P0 清零后执行。
- P2 在不影响 P0/P1 的前提下执行。
- 同一任务不得同时标记多个 Priority。
- 测试执行调度、命令、数据构造、证据保存、失败重试方式不由 planning-layer-runtime 定义。
- planning-layer-runtime 只定义测试设计中的业务顺序、依赖关系、自动化等级、真实环境要求和预期证明对象；实际如何执行由后续测试与验收承接方决定。

## 5. Validation Rules

验收阶段：

- P0 必须全部通过或由 release gate 明确阻断。
- P1 允许有限遗留。
- P2 可进入 backlog。

规则：

- P0 验证失败时不得进入上线通过结论。
- P1 遗留必须说明影响范围、延期原因和后续处理位置。
- P2 遗留必须保留可追踪来源。
- 验收结果必须按 Priority 汇总。
- planning-layer-runtime 不记录测试执行状态或测试结果。

## 6. 文档引用规则

Priority 必须贯穿：

```text
01 -> 04 -> 10 -> 11 -> 12 -> 13 -> 13 确认后派生的 14 / 15
```

引用规则：

| 文档 | Priority 用法 |
| --- | --- |
| 01-需求范围与验收标准.md | 定义需求、范围、验收项的 Priority |
| 04-功能拆解与边界说明.md | 将 Priority 映射到模块和功能边界 |
| 10-外部能力与集成治理.md | 将 Priority 映射到外部能力、Evidence Gate、降级策略和 Runtime Gate |
| 11-测试方案与验收用例.md | 将 Priority 映射到测试范围、验收对象和上线门禁 |
| 12-风险、依赖与待确认项.md | 将 Priority 关联风险、依赖和阻塞项 |
| 13-开发任务合同与落地清单.md | 将 Priority 映射到开发任务、开发依赖和需覆盖验收项 |
| 14-开发执行与联调变更记录.md | 预置按 Priority 追踪的执行事实填写位置，不记录实际完成结论 |
| 15-验收结果与复盘.md | 预置按 Priority 汇总验收事实、遗留项和复盘的位置，不记录实际验收或发布结论 |

规则：

- Priority 的 SoT 为本文档。
- 具体业务项的 Priority 归属由 `01-需求范围与验收标准.md` 定义。
- 下游文档只能引用或映射 Priority，不得重新定义 Priority。
- Priority 不替代 Change Level。
