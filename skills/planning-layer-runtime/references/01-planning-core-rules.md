# 流程梳理阶段核心规则

## 1. 目标

流程梳理阶段的目标不是写代码，而是建立 AI 可稳定理解的开发上下文。

必须确认：

- 当前项目真实处于什么状态
- 为什么做
- 做什么
- 不做什么
- 业务域是什么
- 谁使用
- 角色拥有什么权限
- 数据可见范围是什么
- 怎么流转
- 数据怎么变化
- 接口怎么协作
- 什么情况算完成

## 2. 项目当前基线规则

唯一项目级当前事实文件：

```text
<project_current_baseline_path>
```

职责：

- 记录项目现在真实处于什么状态。
- 区分生产当前状态、已开发但未发布状态、计划中的目标状态。
- 记录旧入口、旧对象、旧状态、旧审批或旧流程的当前处理边界。
- 记录当前前端体验基线及其权威来源，包括布局、导航、通用组件、表单/列表/表格/弹窗/抽屉、空/错/加载/禁用/反馈、移动端与桌面端适配、允许模式、已废弃模式和已知不一致问题。

规则：

- `.runtime/planning-layer-runtime/project-profile.yaml` 只保存 `project_name`、`project_type`、`project_current_baseline_path`。
- 生产当前状态只能由实际发布确认、发布 skill 或用户明确确认更新。
- 已验收未发布不得写成生产已生效。
- 00–13 的计划内容不得反向覆盖项目当前事实。
- 14、15 后续填写的结果可更新当前交付状态，但框架生成本身不能自行把未发布内容标记为生产已生效。
- 已有旧代码、旧接口、旧页面或上一期计划只能作为待核实来源，不得绕过业务规划结论。
- 当前前端体验基线只记录已经真实生效的体验事实和权威来源，不复制完整 CSS、Token、组件代码或设计资产；禁止新建第二份项目级设计基线文件。
- 实际发布后，才允许依据 15 的发布事实更新生产当前状态与当前前端体验事实；已验收未发布仍只属于交付状态。
- 一期关闭后，该期 00–15 进入历史只读；只允许受控修正事实错误，独立新增需求默认从最新 `PROJECT-CURRENT-BASELINE.md` 启动下一期。
- 下一期除最新 `PROJECT-CURRENT-BASELINE.md` 外，还必须读取 `<requirement_pool_path>` 做相关性与冲突判断；池条目只能作为历史需求佐证，不能冒充已实现事实或自动成为本期范围。

一期必须保持以下事实链，不得用最新完整文档覆盖历史执行事实：

```text
当前项目事实
-> Requirement Pool 中与本期输入相关的历史佐证
-> 本期规划基线
-> Planning Execution Baseline
-> Change Set（仅冻结后发生变更时）
-> 执行事实
-> 验收事实
-> 实际发布后的新项目基线
```

## 2.1 规划数据保存边界

Planning 相关数据按职责只允许落在四个位置：

| 位置 | 只允许保存 | 禁止保存 |
| --- | --- | --- |
| `skills/planning-layer-runtime/` | 静态规则、路由、格式规范、职责说明、行为规则与必要 agents 配置 | 运行实例、运行文件复制源、项目、用户、环境、期次、反馈、进度、真实 Event / Decision / Audit 数据 |
| `<phase_planning_runtime_directory>/` | 当前交互状态与本期 Event / Decision / Audit 证据 | 跨期用户画像、跨期环境档案、正式业务事实的替代副本 |
| 项目根目录 `.runtime/planning-layer-runtime/` | 跨期稳定的用户交互倾向、项目与开发环境、启动入口 | 期次需求、业务事实、完整聊天、一次性情绪、凭证、运行日志 |
| `<requirement_pool_path>` | 用户已确认延期、尚待后续期次判断的需求 | 当前项目事实、当前期正式范围、已消费需求、TASK、执行状态、聊天记录或正式 SoT 正文 |

规则：

- 期次级真实运行实例统一进入 `planning-runtime/`，不得再创建语义重复的 `feedback-runtime`、`confirmation-runtime`、`handoff-runtime`、`recovery-state` 或 `context-compression-runtime`。
- Skill 中不得保存 `runtime-*`、用户画像、环境档案、当前交互、Event、Decision、Audit 或 Summary 的独立运行文件；运行时根据 `04-planning-format-spec.md` 的内联字段规范，直接在项目合法目录按需创建。
- 正式业务事实只能进入对应 00–15 SoT；Runtime State、Event、Decision、Audit 和 Summary 均不得替代 SoT。
- `.runtime/planning-layer-runtime/user-profile.yaml` 是用户长期交互倾向的唯一来源，只保存反复体现且具有长期价值的倾向。
- `.runtime/planning-layer-runtime/environment-profile.yaml` 只保存后续 Planning 需要复用的稳定环境事实，例如操作系统、Shell、语言运行时、包管理器、常用工具、技术栈、稳定目录与启动方式、测试/预发布/生产的基本区分。
- `.runtime/planning-layer-runtime/` 禁止保存 Token、密码、私钥、Cookie、主机账号、可识别个人的完整 Home 路径、内网 IP、机器序列号、完整敏感环境变量、生产密钥或可直接调用外部服务的配置。
- 包含本地用户或电脑环境信息的 `.runtime/planning-layer-runtime` 文件默认视为项目本地启动上下文；写入前先检查现有忽略策略，没有明确版本管理要求时建议加入 `.gitignore`，不得未经判断改变项目已有策略。
- `.runtime/planning-layer-runtime/` 和期次 `planning-runtime/` 默认按本地私有数据处理；Skill 打包、分享或上传不得携带这两个项目目录。
- 未得到用户明确要求时，用户倾向、电脑环境和用户原始反馈不得进入公开仓库；项目已有团队共享策略优先，确需共享时只允许共享脱敏后的稳定项目信息。
- `.runtime/planning-layer-runtime/user-profile.yaml` 同时承载长期交互习惯和规划协作偏好，禁止新增第二个长期偏好文件。
- 项目运行文件按需创建：进入 `discovery_start` 且本期路径合法绑定后，必须在第一条实质性业务问题前创建 `current-interaction.yaml`；Event、Decision、Audit 和各类 Summary 只在对应事件、快照、审计或压缩需求真实发生时创建；无内容文件不得为了目录完整性创建。
- `13-开发任务合同与落地清单.md` 是 Planning Execution Baseline 完整正文的唯一承载；首次 13 只读取已确认且适用的 01–12，确认后才在 13 中追加冻结基线区块。
- 完整 Change Set 历史只作为追加式 Decision Snapshot 写入既有 `planning-runtime/decision-log.md`；它是范围准入与增量选择的 Runtime 证据，不是业务 SoT，不得复制完整 00–15 正文。
- `current-interaction.yaml` 保存逐轮 Discovery 检查点，以及 Planning Execution Baseline revision、当前 active Change revision、状态与 `decision_ref` 的最小恢复引用；不保存完整聊天、完整 Baseline、Change Set、TASK 或执行事实。
- 14、15 和 Handoff 只引用 Planning Execution Baseline revision、active Change Set revision 与必要 TASK contract revision，不重复定义其正文。
- `<requirement_pool_path>` 是跨期待处理需求的唯一入口。已确认延期项必须立即写入；15 的下一期输入和 Handoff 只引用 `POOL-ID`，不得复制需求正文形成第二来源。
- Requirement Pool 不是当前项目基线或正式业务 SoT。条目只有经新一期 Discovery 重新核对、确认纳入，并进入当前 Planning Context / 正式 SoT 后，才成为本期事实。

## 3. 最高优先级规则

- 不允许隐式猜测需求、范围、权限、数据结构、接口行为和状态流。
- 高风险不确定项必须停止确认。
- 低风险不确定项允许带假设推进，但必须显式标注。
- 上游文档未确认时，下游文档不得落正式正文。
- 每份文档只负责自己的职责，不允许跨文档写内容。
- 下游发现上游错误时，必须回到上游修正。
- 每份正式文档必须单独生成、单独确认；当前文档未确认前，不得生成下一份正式文档。例外：14、15 是 13 已确认后自动派生的框架对，不作为 13 确认前置，不需要独立生成前协作确认。
- 文档结论必须可追踪到已确认信息。
- 未确认内容不得写成事实。
- 所有关键实体必须具备唯一 ID。
- 所有关键结论必须可追踪到来源。
- 可以从项目证据或公开权威资料核验的客观事实必须先查证；不得把公开事实、当前能力、版本限制或规范内容当作业务问题要求用户回忆。
- 调研证据不能替代用户对内部事实、业务取舍、范围和适用性的确认；公开资料发现的新功能只作为候选，不得自动扩展本期范围。
- 禁止多个文件定义同一事实。
- 禁止混淆计划、验收、已开发未发布和已上线生产状态。
- 状态流必须显式定义。
- 所有跨模块变更必须具备影响分析。
- 面向非专业用户的提问必须使用业务白话，不得直接抛出专业术语。
- UI/交互高风险项未确认时，不得生成依赖该 UI 的开发任务。

## 3.1 结构化 Runtime 规则

关键实体：

- 需求
- 流程
- 状态
- 接口
- 权限
- 风险
- 测试
- 任务

规则：

- 结论格式：`结论 -> 来源`
- SoT 唯一：同一事实只能由一个文件定义
- 状态流：必须定义来源、去向、非法迁移、回滚规则
- 跨模块变更：必须定义影响文档、接口、状态、权限、测试、租户隔离、缓存、历史兼容

## 3.2 Planning Trace ID Boundary

以下 ID 及其包含的期次、阶段、版本或迭代标识，只用于 Planning 追踪：

```text
REQ POOL FLOW SCN DOMAIN MODULE STATE API PERM ARCH CAP TASK TEST RISK DEP OPEN EXEC
```

允许用途：

- 00–15 文档内部及文档之间的引用。
- 14 执行记录与 15 验收记录关联。
- Commit、PR、执行证据和变更说明中的追踪引用。

这些 ID 不是业务名称，也不是技术命名规范。除非用户明确要求版本化实现，且 09 存在单独确认的架构决策，否则期次、Sprint、阶段、版本和 Planning ID 不得直接、缩写、翻译或变形进入长期实现命名。

禁止进入：

- 源码模块、目录、包、命名空间、类、函数、变量和 DTO。
- 数据库表、字段、索引、约束、外键、枚举、ORM Model 和迁移目标名称。
- API 物理路径、权限点、业务事件、消息 Topic、缓存 Key、配置键、环境变量、Feature Flag 和长期测试套件。
- 任何会长期保留在项目中的实现资产。

任何包含期次、阶段、Sprint、迭代或版本编号的标识都只能作为追踪上下文，不得推导代码或数据命名。Planning ID 可以出现在注释和证据中，但不得成为业务对象或技术组件的正式名称。

### 数据域隔离与物理技术域

```text
业务数据域隔离
!= 以期次编号新建数据库表
!= 以期次编号新建代码模块
!= 以期次编号新建 API
!= 以期次编号新建权限体系
```

“新业务事实”“独立数据域”“重新开始”“旧数据不得进入新流程”默认只表示业务语义、数据来源、状态来源、权限与访问范围、新旧流程写入边界、生产/测试数据隔离，以及旧对象不得成为新流程生效来源。

它们不自动表示必须新建物理表、独立模块、复制业务模型、API 命名空间或期次权限点。是否新增物理模型或模块，必须由执行前真实代码架构检查决定，并采用长期稳定的业务领域名称。

## 4. 高风险不确定项

以下内容不明确时，必须停止，不得继续落正式正文：

- 权限规则
- 删除规则
- 数据归属
- 租户隔离
- 数据结构
- 状态流转
- 接口契约
- UI/交互高风险项
- 审计规则
- 旧逻辑是否保留
- 项目当前基线缺失、过期、来源冲突或无法确认
- 生产状态与交付状态无法区分
- 本期目标与旧入口、旧对象、旧流程的关系不明确
- 外部系统真实调用
- 安全、合规、计费、审批相关逻辑

停止后允许输出：

```text
当前理解
-> 阻塞问题
-> 推荐方案
-> 建议确认路径
```

## 5. 低风险不确定项

以下内容不明确时，可以基于假设继续推进：

- 按钮文案
- 空状态文案
- loading 文案
- 图标选择
- 局部样式
- 展示顺序
- 变量命名
- 非核心组件命名
- 低风险 UI 细节

前提：

- 核心页面布局、操作路径、跳转关系、状态反馈、异常态、空状态、加载态、移动/桌面适配和视觉风格已确认。
- 未确认核心 UI/交互时，上述内容不得按低风险假设进入 UI 依赖开发任务。

但必须显式标注：

```text
假设：……
风险等级：低
待确认：是
影响范围：……
回收时机：验收前确认
```

## 6. 文档依赖链

默认链路为：

```text
Project Current Baseline
-> 目标
-> 范围
-> 业务域
-> 角色
-> 权限
-> 数据可见性
-> 用户流程
-> 功能边界
-> 数据模型
-> UI设计
-> 接口契约
-> 权限异常
-> 架构决策
-> 外部能力治理
-> 测试方案
-> 风险依赖
-> 开发任务
-> Planning Execution Baseline
-> 14/15 Framework
-> Handoff
-> 执行与测试事实
-> 验收与发布事实
-> Project Current Baseline 更新
-> 本期关闭
```

03/04/05 相关规划链路固定为：

```text
01 FLOW：业务旅程合同
-> 02：对象、资格、前置与禁止关系
-> 03 SCN：用户场景与可见交互路径
-> 04 MODULE：系统能力模块与隔离边界
-> 05 PAGE / UI-MOD / UX-SCN：页面设计、局部模块设计、UX交互设计
```

规则：

- Project Current Baseline 只提供当前事实，不定义本期目标。
- 下游不得反向覆盖上游。
- 代码实现不能反向定义需求。
- 验收结果不能替代测试方案。
- 执行记录不能替代任务清单。
- Planning Execution Baseline 冻结后，Change Set 只能增量修订受影响合同，不得覆盖既有执行事实。
- Requirement Pool 只参与新一期 Discovery 的输入核对，不得直接插入冻结后的执行队列或替代 Change Set 准入。
- 14、15 中已经由后续阶段填写的事实不得被 Planning 删除、覆盖、重置或重新绑定。
- 未受影响但尚未开始、仍属于原执行基线的 active TASK 必须继续承接，不得因为产生 Change Set 或替换旧 Handoff 而从执行队列丢失。

## 6.2 03/04/05 事实归属与上游写回

唯一职责归属：

- 01 定义 FLOW，拥有合法入口、业务前置、允许步骤、成功终态、禁止跳步和反向验收。
- 02 定义支撑 FLOW 的对象、角色资格、访问上下文、对象关系和旧对象禁止关系。
- 03 定义 SCN，只把 FLOW 展开为用户实际进入、操作、看见、失败、恢复、退出的场景。
- 04 定义 MODULE，说明系统由哪些能力模块承接 FLOW / SCN，每个模块负责什么、不负责什么、依赖谁、隔离谁。
- 05 定义 PAGE、UI-MOD、UX-SCN、设计提示词和设计资产索引，将 SCN 与 MODULE 转化为页面设计、局部模块设计和基于图像的 UX 交互设计。

禁止：

- 03 重新定义主业务旅程、合法入口、成功终态或核心前置。
- 04 重新定义页面、按钮、接口、字段、状态枚举或技术目录。
- 05 擅自改变业务流程、角色资格、对象关系、状态语义或权限规则。

下游发现上游 FLOW、对象关系、资格、前置、终态或禁止路径缺失、冲突或不可实现时：

```text
停止当前文档确认
-> 标记上游 write-back required
-> 回到 01 或 02 修正
-> 不得在下游自行补造业务规则
```

设计协作边界：

- 用户使用的 UI 出图工具属于设计协作工具，不等于产品运行时依赖。
- 不得仅因使用 UI 出图工具而强制创建 Capability Registry。

## 6.3 06/07/08 事实归属与依赖链

06/07/08 相关规划链路固定为：

```text
01 FLOW：业务旅程合同、合法入口、前置、成功终态、禁止路径
-> 02 DOMAIN：业务对象、资格、访问上下文、对象关系、旧对象禁止关系
-> 06 DATA / STATE：业务事实、业务事件、状态分类、迁移守卫、非法迁移、旧状态隔离
-> 07 API：前后端读写合同、请求、响应、拒绝、幂等、并发、接口级旧流程隔离
-> 08 PERM：权限决策、资源范围、数据域、越权拒绝、协助边界、旧对象访问边界
-> 11 TEST：将上述内容展开为自动化与人工测试用例
```

唯一职责归属：

- 06 定义业务数据事实、业务事件、状态分类、状态来源、允许迁移、迁移守卫、非法迁移、旧状态隔离和数据域逻辑边界。
- 07 定义前后端接口合同，包括前端可以读取什么、提交什么，后端必须返回什么、拒绝什么，以及请求/响应语义、错误合同、幂等与并发、旧接口隔离。
- 08 定义访问决策与异常处置边界，包括谁能对什么资源，在什么范围、什么资格、什么状态、什么数据域下执行什么动作，以及越权、协助和历史访问如何处理。

禁止：

- 06 定义页面按钮、弹窗、接口路径、权限矩阵、数据库物理表结构、迁移脚本。
- 07 定义完整角色权限矩阵、页面布局、视觉呈现、数据库实现细节。
- 08 定义接口参数、接口响应字段、页面按钮样式、业务状态枚举、数据库实现。

## 6.5 12/13/14/15 规划收口、任务合同与框架生成链路

12/13/14/15 的未来规划链路固定为：

```text
01–11 已确认的业务、对象、交互、模块、状态、接口、权限、架构、能力与测试设计
-> 12 RISK / DEP / OPEN：所有未闭合事项的唯一正式收口
-> 13 TASK：只接收已确认、可执行、可验证的规划结论
-> 14 EXECUTION RECORD FRAMEWORK：在 13 确认后自动生成执行记录框架
-> 15 ACCEPTANCE RESULT FRAMEWORK：在 13 确认后自动生成验收与复盘框架
```

唯一职责归属：

- 12 是正式 RISK / DEP / OPEN 的唯一 SoT。01–11 只能输出风险信号、风险移交项、阻断提示或待确认问题，不得为同一问题创建多个正式 `RISK-ID`。
- 13 定义任务合同、依赖图、执行前置、并行边界、完成证明要求和 14/15 框架输入。
- 14 在规划阶段只作为后续执行事实的承载框架，预置任务执行、验证、偏差、阻断、回写和交接位置，不填写任何实际执行事实。
- 15 在规划阶段只作为后续验收、真实环境验证、发布判定与复盘事实的承载框架，预置验收对象、门禁、证据位置和基线更新条件，不填写任何实际验收或发布事实。

必须始终区分：

```text
框架已生成且完整
≠ 实际开发完成
≠ 自动化验证通过
≠ 真实环境通过
≠ 最终验收通过
≠ 已发布
≠ 项目当前基线已更新
```

规则：

- 已确认且已有正式 SoT 承接的业务规则，不得再次作为 RISK 或 OPEN 进入 12。
- 关键 OPEN 未关闭，不得生成对应 TASK。
- OPEN 的关闭必须先回写真正拥有该事实的上游 SoT；上游结论确认后，12 才能记录 `resolved` / `confirmed` 及来源。
- 13 不得为能力选型未确认、接口合同未确认、旧流程处理方式未确认或关键 OPEN 未关闭的事项生成任务。
- 候选文件路径不等于已确认实现事实；规划阶段只确认逻辑影响面。
- 只要本期需要生成 13 TASK，就必须同时具备 11 测试设计与验收用例、12 风险/依赖/待决策事项，以及所有被 TASK 引用且已确认的上游 SoT。
- 15 不得作为可独立装配的孤立文档；15 只能在 13 确认后与 14 一起自动派生。
- 13 确认并回写 `状态: 已确认` 后，planning skill 必须生成 14、15 正式框架，并运行 Execution and Acceptance Framework Derivation Gate。
- 14、15 自动派生后不得写入 `文档状态：已确认`，只能写入 `框架生成状态：generated`、`框架完整性：complete`、`用户独立确认：not_required`、`实际事实状态：not_started`。
- 14、15 框架生成后，只向用户输出简洁说明：已生成执行记录框架与验收框架，当前只预置待填事实位置，不代表开发完成、测试通过、可发布或已发布。
- 14、15 框架生成不代表实际开发、验证、验收、发布或基线更新。
