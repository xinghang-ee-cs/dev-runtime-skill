# 流程梳理阶段：文档职责与最小输出

## 1. 文档结构

规划文档使用规范目录，不默认全量生成。

以下文件名是当前建议命名，不是跨 skill handoff 的稳定协议。

跨 skill handoff 必须按文档职责承接，例如 `Development Landing Checklist`、`Capability Governance`、`Execution and Integration Record`、`Acceptance and Retrospective Record`。

根据需求特征动态装配必要文档；L 级跨模块变更或用户明确要求完整规划时，可使用完整建议链路：

```text
00-需求背景与目标.md
01-需求范围与验收标准.md
02-业务域模型.md
03-用户场景与交互流程.md
04-功能拆解与边界说明.md
05-前端页面与UI/UX交互设计.md
06-数据模型与状态流转.md
07-接口设计与前后端契约.md
08-权限、数据可见性与异常处置边界说明.md
09-架构设计与关键决策.md
10-外部能力与集成治理.md
11-测试方案与验收用例.md
12-风险、依赖与待决策事项.md
13-开发任务合同与落地清单.md
14-开发执行与联调变更记录.md
15-验收结果与复盘.md
```

动态装配规则由 `06-planning-capability-governance.md#15-文档装配规则` 定义。

planning handoff 给执行 skill 时，必须显式输出职责到路径的映射，禁止让执行 skill 通过编号猜测文件。

## 2.1 00/01/02 强化职责

### 00-需求背景与目标

职责：只描述"现状到目标"的业务方向。

必须新增：

- 当前项目起点：当前生产中真实生效的流程、已开发但未发布的能力、已废弃或待替换的流程、遗留风险与未完成项、本期从哪里开始、本期完成后预期改变什么。
- 本期变化定位：新建、增补、替换、阻断、迁移、清理。
- 每个变化定位必须写 `结论 -> 来源`。

禁止：

- 定义具体接口、页面、状态枚举、数据库或代码任务。
- 把未发布或未验收能力描述为当前生产事实。
- 跳过已有旧流程的存在与处理定位。

### 01-需求范围与验收标准

职责：本期范围、优先级和业务验收的唯一 SoT。

正文主结构必须使用 `04-planning-format-spec.md` 中的 Flow Contract，并按业务旅程组织，不按功能名平铺。

统一顺序：

```text
合法入口
-> 身份 / 会话 / 访问上下文建立
-> 查询或进入业务工作台
-> 核心业务动作
-> 异常与阻断
-> 当期闭环
-> 后续周期动作
-> 旧流程 / 历史对象边界
```

规则：

- 每个 P0 REQ 必须归属至少一条 FLOW。
- 每条 FLOW 必须有合法入口、起始状态、必要前置、成功终态和禁止跳步。
- 每个业务动作必须说明谁在什么条件下可以做。
- 未认证、无会话、无组织/租户/项目范围、无必要业务上下文时，不得直接查询或提交。
- 无任务、无权限、无上下文、前置未完成时，必须定义阻断结果。
- 必须同时定义正向验收和反向验收。

反向验收至少覆盖：

- 不应发生什么。
- 不允许谁操作。
- 不允许从哪个旧入口进入。
- 不允许依赖哪个旧状态。
- 不允许跳过哪个前置。

### 01 与 03 职责边界

- 01 定义业务旅程骨架、入口、前置、合法步骤、终态、禁止路径和业务验收。
- 03 只展开用户交互步骤、异常分支、页面反馈和终止条件。
- 03 不得新增 01 未定义的主业务旅程。
- 03 不得改变 01 的合法入口、核心前置、成功终态或禁止路径。
- 如 03 发现 01 缺少必要业务旅程或前置，必须使 01 回到待修正状态。

### 02-业务域模型

职责：定义业务实体、关系、归属、生命周期和业务域权限关系，并证明 01 的旅程不能跳步。

必须新增：

- 旅程—对象关系地图。
- Access Context。
- 当前对象与目标对象处理矩阵。
- 关键旧对象或旧流程对新流程的负向对象关系。

规则：

- 02 必须严格按 01 的 FLOW 顺序生成。
- 01 每条 FLOW 都必须在 02 中有对应关系行。
- 若 01 的前置、动作或终态在 02 无对应对象或关系支撑，则 02 不得确认。
- 若 02 新增了会改变 01 旅程的对象关系，则必须回到 01 修正。

## 2.2 03/04/05 职责边界

### 03-用户场景与交互流程

核心 ID：

```text
SCN-<DOMAIN>-<SEQ>
```

职责：只回答用户在什么条件下进入、看见什么、做什么、系统反馈什么、失败后能做什么，以及如何恢复、退出、重试或进入人工协助。

03 不拥有：

- 主业务旅程定义。
- 业务终态定义。
- 权限资格定义。
- 状态迁移定义。
- 接口契约定义。
- 审批后生效、直接生效或其他生效口径判断；03 只能引用 01 的 FLOW 结论。

场景顺序必须严格继承 01 的 FLOW 顺序：

```text
身份/会话与访问上下文
-> 进入业务入口或工作台
-> 核心操作
-> 异常与阻断
-> 当前周期闭环
-> 后续周期操作
-> 旧入口与历史对象
```

03 不得默认用户已登录、已有会话、已有组织/租户上下文、已有项目、资源或业务范围，或天然有操作资格。若这些前置由既有系统提供，也必须写清楚“由既有体验承接”，以及恢复成功后进入哪个 PAGE。

### 04-功能拆解与边界说明

04 只定义系统能力模块，不定义用户页面或技术实现。

模块类型：

- 核心业务能力模块：工作台、打卡证据、留痕、闭环、明日计划、第二天任务开始等。
- 横向边界模块：访问上下文、资格边界、异常补充、旧流程隔离、数据域隔离、质量门禁等。
- 外部能力适配依赖：只表达依赖关系，不定义 SDK、版本、鉴权、真实调用或 Provider 细节；这些属于 10。

每个模块必须说明：

- 它承接哪些 FLOW / SCN。
- 它读取哪些已确认业务事实。
- 它向其他模块提供什么业务能力。
- 它不负责什么。
- 它依赖什么。
- 它必须隔离什么旧模块、旧语义或旧对象。

旧对象处理只允许：

```text
inherit
adapt
create
deprecate
block
readonly
cleanup
```

禁止使用“尽量兼容”“视情况复用”“可能保留”“后续再看”。

### 05-前端页面与UI/UX交互设计

如项目仍保留旧文件路径 `05-前端页面与UI交互设计.md`，正文标题和职责必须使用“05-前端页面与UI/UX交互设计”。

05 是：

```text
UI 设计流程启动文档
+ UX 交互设计承接文档
+ 设计提示词交付文档
+ 设计资产索引文档
```

双层确认：

- 交互合同确认：确认页面承接什么 SCN、页面状态、主次操作、禁用操作、异常恢复和旧入口处理。
- 视觉资产确认：确认风格图、完整页面图、局部模块图、UX交互图是否已经收到、审阅、确认或需要重做。

规则：

- 05 文档可以在“交互合同已确认”后进入已确认状态。
- 每一张设计图、每一个页面视觉方案、每个 UX 图都必须有独立资产状态。
- 设计资产已生成不等于页面已开发、页面已测试、页面已验收或已上线。
- UI 依赖开发任务只能在所需页面或模块资产达到 `visual_confirmed` 后生成或进入可执行状态。
- 不依赖 UI 的后续规划文档不应被无故阻塞。
- 用户未提供图时，资产只能是 `planned` 或 `prompt_ready`。

05 设计流程：

```text
03 SCN + 04 MODULE 已确认
-> 生成 05 文档草案
-> 输出设计范围、页面优先级、资产计划
-> 主动生成全局风格统一性提示词
-> 用户确认或提供风格参考
-> 按 P0 FLOW / SCN 顺序逐页生成完整页面提示词
-> 用户生成或提供页面 UI 图
-> 回写设计资产索引
-> 针对局部状态变化生成模块化设计提示词
-> 用户生成或提供模块 UI 图
```

## 2.3 06/07/08 职责边界

### 06-数据模型与状态流转

核心定位：

```text
业务事实与状态合法性的唯一 SoT。
```

06 必须区分状态分类：

- `domain_state`：持久业务状态，例如已提交、已生效、已关闭。
- `derived_action_state`：由业务状态、资格、上下文和异常事实推导出的当前可做什么状态，例如当前可提交、当前需补资料。
- `interaction_state`：UI 暂态，例如确认弹窗打开、提交中、上传中、重试中；默认由 03 / 05 管理，只有确实需要持久化、断点恢复或审计时，才可升为 06 状态。
- `exception_state`：业务或外部能力失败后需要恢复、补充或人工协助的状态。
- `legacy_boundary_state`：旧入口、旧对象、旧审批、旧状态的只读、阻断、迁移或清理边界。
- `data_domain_state`：测试、预发布、生产等数据域及其隔离状态。

规则：

- “字段”只能表示业务逻辑所需事实，不得定义表名、字段类型、长度、索引、外键、SQL、ORM Schema 或迁移脚本。
- 05 定义的 UI 暂态不得自动成为 06 的业务状态。
- 前端、路由、本地缓存、旧审批记录、旧入口来源不得自行生成或伪造状态。
- 派生动作状态必须由后端根据真实业务状态、资格、上下文和异常事实稳定推导。
- “没有任务”不得直接迁移为“可打卡”或其他可写状态；必须通过任务已分配、上下文完整和用户具备资格等业务事实重新计算可执行状态。

- 07 只声明接口所需的访问上下文、业务资格、状态与事实前置。
- 07 不得重写完整权限矩阵、数据可见范围策略或越权展示策略。
- 07 定义 Canonical API Contract；09 定义 Architecture Binding / Implementation Boundary。
- 若 Canonical API Contract 发生改变，必须回写 07，并触发 08、11、13 等下游失效传播。

### 08-权限、数据可见性与异常处置边界说明

正式定位：

```text

```

访问决策：

```text

+ 目标动作
+ 目标资源

+ 当前业务状态
+ 当前数据域
```

规则：

- 前端隐藏、禁用或不展示按钮，只是体验。
- 08 定义的 PERM 决策必须由后端或服务端边界实际执行。
- 任何前端、接口参数、来源参数、旧审批记录、旧入口、管理员身份都不得绕过 PERM 决策。
- 工作人员协助只能用于诊断、技术恢复、引导用户回到正常路径；不得代替用户提交业务动作、直接修改正常业务状态或代替业务资格主体生效。
- 若确实需要人工改变业务事实，必须回到 01、02、06 定义新的合法业务事件，不得由 08 默认放行。
- 旧对象没有任何新流程 COMMAND 权限；历史记录只有在满足 HISTORICAL_READONLY 范围时允许读取。
- 旧对象、旧审批、旧状态不得作为新流程状态、资格、前置或生效来源。

- 框架已经生成，预置项已经完整。
- 用户不需要单独确认 15。
- 真实验收、发布和基线事实尚未填写。

### 13 确认后的框架生成规则

13 被用户确认并回写 `状态: 已确认` 后，planning skill 必须自动生成 14 和 15 的正式框架。

唯一顺序：

```text
12 已确认
-> 生成 13 草案
-> 用户确认 13
-> 回写 13：已确认
-> 自动触发 14、15 框架派生
-> 自动生成 14 与 15 的正式框架
-> 对 14、15 运行 Execution and Acceptance Framework Derivation Gate
-> 汇总实际已生成的 assembled_documents
-> 基于实际路径生成 handoff_role_mapping
```

规则：

- 14、15 只生成框架和预置空白项。
- 14、15 自动生成后不得写入 `文档状态：已确认`。
- 14、15 只能写入 `框架生成状态：generated`、`框架完整性：complete`、`用户独立确认：not_required`、`实际事实状态：not_started`。
- 14、15 不填写任何实际执行、验证、验收、真实环境或发布事实。
- 14、15 不得反向定义业务、状态、接口、权限或测试标准。
- 14、15 的实际事实只能由后续执行或验收承接方填写。
- 14、15 不触发“每次只能生成一份正式文档”的限制。
- 14、15 不需要分别进行生成前协作确认。
- 14、15 不需要把独立用户确认作为 Planning 完成前提。
- 不新增独立风险 Runtime、任务 Runtime、执行 Runtime、验收 Runtime、日志体系或治理目录。

## 3. 文档结构化依赖模板

每份文档必须包含：

```markdown
## 上游 SoT

- xx-文档名.md#ID

## 下游输出

- xx-文档名.md#ID

## 禁止定义内容

- ...
```

## 4. 阶段分界

00 到 13 属于流程梳理阶段，planning-layer-runtime 的职责截止于开发开始前。

14、15 在 planning-layer-runtime 中只属于 13 确认后派生的框架承载文档。

14、15 中的实际执行、验证、验收、真实环境、发布和基线更新事实，由后续执行承接方或后续测试与验收承接方填写。

## 5. Planning Runtime Final Output

Planning Runtime 最终输出：

```text
1. Planning Context
2. Formal SoT Documents
3. assembled_documents
4. handoff_role_mapping
```

Handoff 承接规则：

- 后续承接方只能按 `handoff_role_mapping` 中实际存在的职责和路径承接。
- 禁止通过编号猜测文件。
- 禁止自行推断职责。
- 禁止缺失 role 时继续 implementation。
- `handoff_role_mapping` 属于规划交接输出，不属于业务 SoT。
