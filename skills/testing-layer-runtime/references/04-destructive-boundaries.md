# Destructive Boundaries

## 总原则

破坏性测试是指可能删除、覆盖、污染、重置、压垮、锁死、泄露或不可逆改变数据、文件、服务、账号、权限、外部资源或环境状态的测试。

默认先选择非破坏性验证。必须使用破坏性逻辑时，先明确：

```text
破坏性对象：
目标环境：
隔离方式：
可回滚方式：
影响范围：
执行命令或操作：
二次确认：
```

没有用户二次确认，不执行破坏性命令或操作。

系统风险 Profile 定义需要证明什么，不授予额外操作权限。线上运行测试可以选择获准隔离预发布环境；它仍服从本文件对该环境实际操作的边界。服务器禁止的 shell、故障注入、部署或回滚操作交给项目授权责任主体执行并返回证据，Testing 不自行执行。下方“上线测试”的授权压力/安全测试仅指外部受控交互，不豁免服务器/生产禁项；无法取得所需证明时保持未验证或阻塞，不用 smoke 或配置存在性补偿。

## 自动化重跑例外

允许：

- mock、fixture、临时对象、事务回滚、内存仓储、测试库中的破坏性逻辑。
- 明确测试库中的创建、更新、删除和异常路径验证。
- 仅在 Automated Result Reuse Rule 允许重新执行时适用；默认自动化执行仍属于 long-task-orchestrator。

禁止：

- 未确认测试库隔离时执行数据删除、迁移重置、批量清理或真实外部资源修改。
- 使用生产或共享开发数据作为可破坏对象。

## 本地环境测试

允许：

- 本地隔离测试数据、mock 外部能力、本地测试库、临时上传文件和可清理缓存。
- 为验证异常流程执行可控的失败注入或状态重置。

限制：

- 本地破坏性命令必须先说明影响并取得用户二次确认。
- 涉及数据库 reset、删除文件、清空缓存、关闭服务、修改系统设置、修改真实 `.env.local` 时必须停止确认。
- 本流程启动的本地端口必须在结束前关闭。

## 服务器环境测试

允许：

- 只允许数据库层面的破坏性测试逻辑，且必须限定在用户确认的服务器测试数据、测试租户、测试账号或测试库范围内。
- 优先使用可回滚事务、测试租户、一次性测试记录和明确清理语句。

禁止：

- 破坏性服务器 shell 命令。
- 删除部署目录、重启非目标服务、修改 nginx/systemd、清理生产文件、改生产环境变量。
- 对外部 SaaS、真实用户数据、真实账号权限、对象存储、支付、消息推送等执行破坏性操作。
- 本地指令直接触发未确认的服务器破坏性行为。

## 上线测试

只允许外部交互逻辑：

- 正常访问、登录、浏览、提交授权范围内的测试数据。
- 受控、授权、限速、可停止的压力测试和安全测试。
- 只读或非破坏性的安全探测。

禁止：

- 数据删除、批量写入、漏洞利用、绕过认证、权限提升、账号枚举、密码爆破、恶意 payload、DDoS 或任何不受控流量。
- 对生产数据、生产账号、真实用户、真实外部资源执行破坏性测试。

## 严重警告条件

发现以下任一情况，立即输出 `严重警告`，停止放行，并建议进入项目定义的发布/安全流程或专项安全处置：

- 可越权访问其他组织、租户或用户数据。
- 认证、授权、回调、token、state、session 或 CORS 存在可利用缺口。
- 日志、页面、接口或截图暴露密钥、token、精确位置、隐私数据或外部平台身份。
- 压测导致服务不可用、数据异常、队列堆积、数据库锁死或成本异常。
- 出现疑似攻击、扫描、撞库、异常流量或蓄意破坏迹象。
